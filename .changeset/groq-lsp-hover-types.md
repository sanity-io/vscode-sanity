GROQ hovers show the type the generated types give more of a query, via `@sanity-labs/groq-lsp` 1.4.1 (`@sanity-labs/groq-lint` 1.3.1 and `@sanity-labs/lint-core` 1.0.3). A call to a built-in such as `count(…)`, `defined(…)`, `coalesce(…)`, `select(…)` or `pt::text(…)` shows what the call returns next to the function's documentation, and a pipe function such as `| order(…)` shows the array it returns. The start of a chain that continues after it shows its type: `slug` in `*[_type == "post"].slug.current` or `showcaseProjects[]->slug.current`, `order` in `*[…] | order(…) {…}`, and `tags` in `{tags[0]}` or `{tags[]}`. String and number literals print the way the generated types do, so `'It\'s'` shows `"It's"` and `2.50` shows `2.5`. A query parameter hovers as the `QueryParams` type the content mapper generates for it, including a parameter in a query whose root is an object, the bounds of `x in $min..$max`, an arithmetic operand, and a comparison with a literal. A field read through `^` in a filter over an array of strings or numbers, such as `tags` in `tags[@ in ^.tags]`, shows its type. Field, projection key and custom function call hovers follow the query's syntax tree, so they match `QueryResponse` on queries whose root is an object, after a `//` comment, and inside `select()` and conditional attributes. A missing field hovers as `null`, `true`, `false` and `null` hover as literals, and types print as `sanity typegen` does (`never` for an empty union, quoted names, `_key` on arrays of named types).
